# RansomShield AI — Phase 1 Validation Report

## 1. Overall Status

FAIL

Phase 1 is functionally implemented and the ML pipeline passes its local automated tests, but it is not ready for Phase 2 because the dataset is generated synthetic benchmark data with no verified external provenance and the class separation is intentionally engineered to be highly separable. This means the current historical metrics are not a valid estimate of real-world production performance.

## 4. Leakage Audit

### Target leakage
PASS

Why: The feature matrix excludes the `label` column, and the training pipeline uses `df[FEATURE_NAMES]` as the feature set. There is no direct use of the target as an input feature.

### Train/test overlap
PASS

Why: There are 0 duplicate rows in the dataset, and the pipeline uses a stratified train/test split from a single data frame. No row-level duplication was detected across the split boundary.

### Preprocessing leakage
PASS

Why: The `FeaturePreprocessor` is fit only on the training subset before transformation, and the holdout set is transformed using the fitted statistics only.

### Feature leakage
WARNING

Why: Several features are generated as direct class proxies (for example, `write_entropy_avg`, `high_entropy_ratio`, `shadow_copy_tamper`, `registry_write_rate`, `unsigned_proc_ratio`). A synthetic benchmark generator intentionally creates near-disjoint value ranges for each class, which is not a realistic telemetry boundary and can create trivial class separation.

### Temporal leakage
WARNING

Why: There is no timestamp column and no chronological split. The code does not model temporal drift or holdout windows. This is acceptable for a static benchmark, but it is not realistic for ransomware detection deployment.

| Feature | Source | Window | Collection Method | Feasible? |

Notes:
- `unsigned_proc_ratio` is technically feasible but requires additional Windows signature validation logic beyond basic `psutil` data. It is not a simple local metric from process sampling alone.
- `registry_write_rate`, `network_connection_count`, and `shadow_copy_tamper` are feasible with Sysmon/Event Log integration.
- The code uses this as a feature contract, but the generation of training data is not tied to a real endpoint telemetry collection stack.

- Accuracy: 99.96%
- Macro F1: 99.91%

These metrics are unusually high, but they are not evidence of production readiness. The likely causes are:

1. Synthetic benchmark generation with intentionally separate class distributions.
2. Directly engineered features that strongly encode class identity.
3. Easy class separation in the generator logic (for example, benign values vs ransomware values are generated from clearly different distributions).
4. No real-world temporal structure or production telemetry distribution.

This is historical dataset performance only, not real-world production accuracy.

## 12. Problems Found

### CRITICAL

- The dataset is synthetic and generated by repository code; no verified external provenance exists.
- The benchmark generator intentionally creates highly separable distributions, which means the model is solving an easy synthetic problem instead of a realistic Windows endpoint detection task.
- Historical metrics are not production-valid and are not a reliable estimate of real-world generalization.

### WARNING

- Feature leakage risk is elevated because many features are direct class proxies generated from deterministic distributions.
- There is no chronological or time-based holdout validation, so temporal drift is not represented.
- `unsigned_proc_ratio` requires additional Windows signature validation; it is not trivial to collect from process telemetry alone.

### INFO

- The actual ML pipeline and saved artifacts are internally consistent.
- The pytest suite passes under the current benchmark setup.
- The feature ordering and saved metadata are aligned.

## 13. Phase 2 Readiness

NOT READY FOR PHASE 2

The exact issues that must be fixed before Phase 2:

1. Replace the synthetic benchmark dataset with a real-provenance dataset or a clearly labeled benchmark with explicit origin metadata.
2. Validate feature realism against actual Windows telemetry collection, especially `unsigned_proc_ratio` and shadow-copy detection.
3. Add realistic time-ordered validation and drift-aware holdout design.
4. Reassess class separation and leakage risk before treating the current metrics as evidence of model quality.
5. Document the source and assumptions for all telemetry features so Phase 2 uses a defensible feature contract.
